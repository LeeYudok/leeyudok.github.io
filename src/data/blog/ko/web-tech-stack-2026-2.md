## 1탄 채점표

1탄에서 "검토해볼 만한 부분" 네 가지와 "주목할 트렌드" 세 가지를 적었습니다. 하나씩 봅니다.

| 1탄에서 한 말 | 실제로 한 일 | 판정 |
|---|---|---|
| Axios는 fetch로 충분할 수 있다 | 새 프로젝트 넷 모두 Axios가 없다 | 맞음 |
| Recharts는 잘 돌면 유지 | 차트가 필요한 곳은 Recharts 3.10 그대로 | 맞음 |
| 규모가 커지면 Zustand + TanStack Query | 문서 검색에 둘 다, 조기경보 데모에 TanStack Query | 맞음 |
| 라우터는 React Router나 TanStack Router | 셋이 React Router. TanStack Router는 안 썼다 | 절반 |
| RSC를 Vite에서 쓰는 방법이 늘 것 | 한 번도 안 썼다 | 빗나감 |
| 새 프로젝트면 Biome을 고려 | Biome 대신 oxlint를 한 곳에. 나머지는 린터가 없다 | 빗나감 |
| Bun을 이미 쓰고 있다 | 패키지 관리는 전부 pnpm으로 옮겼다 | 뒤집힘 |

맞힌 것은 "빼도 된다"와 "그대로 둬도 된다" 쪽이었습니다. 빗나간 것은 "새것이 온다" 쪽이었습니다.

### Axios는 사라졌다

네 프로젝트 어디에도 Axios가 없습니다. 요청은 전부 `fetch`로 보냅니다. 재시도, 캐시, 로딩 상태는 TanStack Query가 다루니 `fetch`를 감싼 함수 하나면 됩니다.

1탄에서 대안으로 적은 ky도 쓰지 않았습니다. 3KB짜리 래퍼조차 필요가 없었습니다.

### 상태 관리는 서버 상태부터 들어왔다

1탄은 Zustand를 먼저 적고 TanStack Query를 다음에 적었습니다. 실제 순서는 반대였습니다.

화면이 가진 상태의 대부분은 서버에서 온 데이터입니다. 그것을 TanStack Query로 옮기고 나니 전역으로 들고 있을 것이 거의 남지 않았습니다. Zustand는 네 프로젝트 중 한 곳에만 있습니다.

### RSC는 쓸 일이 없었다

네 프로젝트 어디에도 화면을 서버에서 그릴 Node 프로세스가 없습니다. API는 Go 서버가 맡고, 화면은 정적 파일입니다.

이 구조에서 RSC는 얻는 것보다 잃는 것이 큽니다. 배포물이 바이너리 하나와 정적 파일 폴더로 끝나는 단순함이 사라집니다. 1탄은 React 19의 `use()`와 Actions를 장점으로 적었습니다. 네 프로젝트의 소스를 검색해 보니 `use()`, `useActionState`, `useOptimistic`을 쓴 곳이 한 군데도 없었습니다.

### Biome이 아니라 oxlint, 그리고 린터 없음

Biome은 린트와 포맷을 합친 도구입니다. 막상 필요했던 것은 린트뿐이었고, 그래서 더 작은 oxlint를 골랐습니다. `package.json`의 스크립트가 `"lint": "oxlint"` 한 줄입니다.

나머지 세 프로젝트에는 린터가 없습니다. `tsc`가 타입을 보고, 테스트가 있는 곳은 Vitest나 Playwright가 동작을 봅니다.

### Bun에서 pnpm으로

1탄은 "이미 Bun을 쓰고 있다"로 끝났습니다. 지금은 네 프로젝트 모두 `packageManager` 칸에 pnpm이 적혀 있습니다.

바꾼 이유는 속도가 아니라 배포였습니다.

- 빌드를 컨테이너 안에서 합니다. `node:<버전>-slim` 단계에서 `pnpm install`과 `pnpm build`를 끝내고, 최종 이미지에는 결과물만 옮깁니다. 배포 서버에는 Node도 Bun도 깔지 않습니다.
- 의존성 취약점을 점검하고 버전을 올리는 절차를 pnpm 기준으로 만들어 두었습니다. 프로젝트마다 도구가 다르면 그 절차를 두 벌 유지해야 합니다.
- CI에서 `pnpm install --frozen-lockfile`로 락파일과 다르면 실패하게 둡니다.

Bun이 없어진 것은 아닙니다. 문서 뷰어 같은 작은 도구 두 개는 지금도 Bun으로 돕니다. 배포하는 프로젝트의 기본값이 pnpm으로 바뀌었습니다.

## 버전이 프로젝트마다 다르다

위 표에서 TypeScript는 5.8, 5.9, 6.0, 7.0이 한꺼번에 나옵니다. Vite는 6과 8이 같이 있습니다. 모두 2026년에 손댄 프로젝트입니다.

1탄은 "최신 버전 사용 중"을 칭찬으로 적었습니다. 그 말의 유효기간은 석 달쯤이었습니다. 3월에 최신이던 Vite 7은 지금 쓰는 프로젝트가 하나도 없습니다. 6에 멈춘 것과 8로 시작한 것만 있습니다.

프로젝트는 만든 날의 최신에서 멈춥니다. 그 뒤로는 올릴 이유가 생길 때만 올립니다. 문서 검색이 Vite 6에 있는 것은 잘 돌고 있어서입니다.

## 겪은 함정

### pnpm 버전은 배포 서버의 Node에 맞춘다

pnpm 11부터는 Node 내장 모듈 `node:sqlite`를 씁니다. Node 22.13 이상이 필요합니다.

배포 서버의 Node가 배포판 기본값인 20대였을 때, 최신 pnpm은 `ERR_UNKNOWN_BUILTIN_MODULE`을 내고 죽었습니다. 그 뒤로 `package.json`의 `packageManager`와 서버에 깔린 pnpm을 같은 버전으로 고정합니다. 위 표에서 pnpm 버전이 프로젝트마다 다른 것은 그 고정의 결과입니다.

### index.html을 인증 예외 경로에 두지 않는다

백엔드가 로그인 검사를 하면서 `/static/` 같은 정적 경로만 검사에서 빼 두는 경우가 많습니다. Vite 결과물을 통째로 그 경로에 올리면 `index.html`도 로그인 없이 열립니다.

`assets/` 폴더만 예외 경로에 올리고, `index.html`은 로그인이 걸린 주소에서 따로 읽어 내보냅니다. Vite 설정의 `base`를 그 정적 경로에 맞춰야 스크립트 주소가 맞습니다.

### 화면은 바뀌는데 상태가 남는다

같은 컴포넌트를 다른 데이터로 다시 쓸 때 `key`를 주지 않으면 React는 컴포넌트를 새로 만들지 않습니다. 앞 화면의 입력값과 실행 기록이 그대로 남습니다.

순정 JS로 짠 화면을 React로 옮기다가 만난 버그입니다.

### 백엔드 검사만 있는 CI는 프론트가 깨진 것을 모른다

백엔드 문법 검사와 테스트만 돌리는 CI는 프론트 빌드가 깨져도 초록색입니다. 검증 단계에 아래 두 줄을 넣었습니다.

```bash
pnpm --dir web install --frozen-lockfile
pnpm --dir web build
```

### 빌드를 잊고 옛 결과물을 본다

고쳤는데 화면이 그대로면 대개 빌드를 안 한 것입니다. 로컬 실행 스크립트가 `src/`가 `dist/`보다 새로우면 스스로 `pnpm build`를 돌리게 했습니다.
