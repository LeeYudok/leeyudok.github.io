![100만 라인 코드베이스, 에이전트는 모듈 경계로 관리한다](@/assets/images/dev/million-line-agents-cover.png)

100만 라인부터는 사람도 전체를 모릅니다. 그래서 에이전트에게 전체 맥락을 주려는 시도를 버려야 합니다. 대신 필요한 조각만 정확히 찾아 주는 체계를 설계합니다.

이 글은 측정 보고서가 아니라 설계 원칙을 정리한 글입니다. 기준 숫자(200줄, 50%, 주 1회)는 제가 쓰는 눈금이고 실험으로 얻은 값이 아닙니다.

## 규모가 바꾸는 것

| 항목 | 10만 라인 이하 | 100만 라인 이상 |
|---|---|---|
| 전체 맥락 | `CONTEXT.md` 하나로 설명할 수 있다 | 사람도 몰라서 설명할 수 없다 |
| 컨텍스트 공급 | 문서를 통째로 읽힌다 | 심볼·모듈 단위로 검색해 준다 |
| 코드 인덱싱 | 과하다 | 필수에 가깝다 |
| 안전망 | 사람 리뷰 | 테스트와 CI가 1차 방어선 |
| 작업 단위 | 기능 하나 | 모듈 경계 안의 기능 하나 |
| 에이전트 수 | 세션 하나 | 모듈별 병렬 + 통합 검증 |

작은 저장소에서 과했던 검색 인프라가 이 규모에서는 필요해집니다. 100만 라인을 grep과 마크다운만으로 버티면 오히려 준비가 모자랍니다.

## 대원칙: 아키텍처가 컨텍스트 전략이다

100만 라인에서 에이전트 성능을 정하는 것은 프롬프트가 아니라 모듈 경계입니다.

- **모듈 경계가 컨텍스트 경계입니다.** 에이전트가 한 작업에서 읽을 코드가 모듈 하나(수천~수만 라인)에 갇히도록 경계를 잡습니다.
- 순환 의존이나 모든 것을 아는 거대 모듈(god module)이 있으면 어떤 컨텍스트 전략도 통하지 않습니다.
- 그래서 에이전트를 들이기 전에 모듈화 리팩토링이 먼저일 수 있습니다. 도메인별로 나누고, 모듈끼리는 API 계약이나 이벤트 스키마 같은 명시적 인터페이스로만 통신하게 합니다. 인터페이스 정의 파일은 별도 디렉터리에 모아 에이전트가 먼저 읽게 합니다.

은행 시스템은 경계가 계정계, 정보계, 채널계로 이미 나뉘어 있습니다. 이런 곳에서는 그 경계를 에이전트 작업 경계로 그대로 쓰는 것이 가장 안전합니다.

## 문서 계층을 3단으로

| 단계 | 파일 | 담는 것 |
|---|---|---|
| L0 | `/CONTEXT.md` | 전사 지도. 200줄 이내. 도메인 목록, 모듈 지도, 어디에 무엇이 있는지만 적는다 |
| L1 | `/domains/payment/AGENTS.md` | 도메인 규칙. 불변 규칙, 금지 사항, 담당 인터페이스 |
| L2 | `/domains/payment/settlement/AGENTS.md` | 모듈 실무 지침. 코딩 규칙, 테스트 방법, 자주 밟는 함정 |

L0의 역할이 바뀝니다. 작은 저장소에서 `CONTEXT.md`는 내용이었습니다. 100만 라인에서는 목차입니다. 에이전트가 L0을 읽고 관련 L1, L2로 가도록 설계합니다.

여기에 두 가지를 더합니다.

- `docs/decisions`: 설계 결정 기록(ADR). 규모가 커질수록 더 중요합니다.
- `docs/contracts`: 모듈 간 인터페이스 계약 명세.

문서가 낡았는지는 CI로 검사합니다. 문서가 가리키는 파일과 심볼이 실제로 있는지 확인하면 됩니다. 이 규모에서는 사람이 문서를 손으로 관리할 수 없습니다.

## 검색 인프라

용도별로 나눠서 들입니다.

### 1. 코드 검색 — 정확한 것 찾기

가장 먼저 들입니다. 두 가지가 필요합니다.

- 심볼 인덱싱: LSP, ctags, tree-sitter
- 저장소 전문 검색: Sourcegraph, Zoekt. 최소한 ripgrep과 이름 규칙

 에이전트에게는 파일을 통째로 읽지 말고 심볼 단위로 조회하라고 지침과 도구를 줍니다.

### 2. 의미 검색 — 비슷한 것 찾기

벡터DB는 "이런 기능 비슷한 게 어디 있었지?"를 찾는 용도로만 씁니다. 인덱싱 대상은 코드 전체보다 문서, 커밋 메시지, ADR이 먼저입니다. 자연어라서 임베딩이 잘 맞고 잡음이 적습니다. 코드는 원문 조각보다 모듈 단위 요약본을 인덱싱하는 편이 낫습니다.

### 3. 저장소 지도

디렉터리 구조와 모듈별 한 줄 설명을 스크립트로 만듭니다. 세션을 시작할 때 이 지도를 주면 탐색 비용이 줄어듭니다.

### 벡터DB가 늘 이득은 아니다

질의 종류에 따라 이기는 도구가 다릅니다.

- 정확 검색("이 함수의 정의와 호출부가 어디인가")은 LSP와 grep이 낫습니다. 결과가 결정적이고, 늘 최신이고, 운영 비용이 없습니다.
- 개념 검색("환불과 비슷한 로직이 있었나")은 벡터DB가 낫습니다.

에이전트가 작업 중에 던지는 질의는 대부분 정확 검색입니다. 벡터DB가 이기는 구간은 생각보다 좁습니다.

벡터DB에는 고유한 위험이 세 가지 있습니다.

1. **낡은 인덱스.** 재인덱싱이 코드 변경을 따라가지 못하면 인덱스는 틀린 결과를 돌려줍니다. "결과 없음"이 아닙니다. 에이전트가 지워진 함수를 참조하게 됩니다.
2. **코드 임베딩의 약점.** 임베딩 모델은 자연어 중심으로 학습했습니다. 코드에서 생김새가 비슷한 것과 뜻이 이어진 것을 잘 가르지 못합니다. 품질이 조각 나누는 방식에 따라 크게 달라집니다.
3. **컨텍스트 오염.** 상위 k개 검색은 늘 무언가를 돌려줍니다. 그럴듯하지만 무관한 조각이 컨텍스트에 들어오면 없는 것보다 나쁩니다.

정리하면 정확 검색이 기본이고 벡터 검색은 개념 검색에만 씁니다. 들일지 말지는 "grep으로 못 찾아 고생한 개념 검색이 일주일에 몇 번인가"로 판단합니다. 주 1회가 안 되면 100만 라인이어도 아직 이릅니다.

모든 대화를 자동으로 기억하는 범용 메모리 도구는 규모가 커져도 조심합니다. 무엇이든 쌓으면 쓸 것을 찾기 어려워집니다. 저장은 자동화하되 대상을 ADR, 계약, 요약처럼 구조가 있는 것으로 한정합니다.

## 테스트와 CI가 안전망이다

100만 라인에서 사람이 에이전트의 모든 변경을 이해하고 리뷰할 수는 없습니다. 검증의 무게를 사람 눈에서 자동 검증으로 옮깁니다.

- **계약 테스트(contract test).** 모듈 간 인터페이스가 깨지면 바로 실패합니다. 에이전트가 모듈 안을 크게 고쳐도 경계만 지키면 안전합니다.
- **영향 범위 테스트(affected-only).** Nx, Bazel, Turborepo 같은 도구의 빌드 그래프로 바뀐 모듈과 그 모듈에 의존하는 모듈만 테스트합니다. 반복 작업이 빨라집니다.
- **완료 기준은 CI 통과.** 작업 지시서의 완료 조건을 "테스트 통과, 린트 통과, 계약 테스트 통과"로 적습니다.
- **레거시는 특성화 테스트부터.** 테스트 커버리지가 낮은 모듈은 에이전트를 투입하기 전에 현재 동작을 테스트로 고정합니다.

## 작업 지시서에 모듈 경계를 적는다

| 항목 | 이 규모에서 더할 것 |
|---|---|
| 목적 | |
| 작업 모듈 | `domains/payment/settlement` 안에서만 |
| 읽어야 할 것 | 관련 계약 문서, ADR 번호 |
| 변경 금지 구역 | 인터페이스 파일, 다른 모듈 전부 |
| 제약 조건 | |
| 완료 기준 | CI 통과와 계약 테스트 통과 |

변경 금지 구역이 핵심입니다. 에이전트는 문제를 풀려고 경계 밖 파일을 건드리곤 합니다. 경계 밖 수정이 필요하면 작업을 멈추고 보고하라고 지시서에 적습니다. 그 수정은 별도 지시서와 별도 세션으로 처리합니다.

## 세션과 에이전트 운영

**컨텍스트 예산을 더 아낍니다.** 컨텍스트가 50%에 닿으면 세션을 넘기는 규칙은 그대로 둡니다. 다만 100만 라인에서는 그 지점에 훨씬 빨리 닿습니다. 파일을 통째로 읽지 않고 심볼 조회와 부분 읽기를 씁니다.

**탐색과 수정을 다른 세션으로 나눕니다.** 탐색 세션의 산출물은 "수정 대상 파일·심볼 목록과 접근 방법" 문서입니다. 이 문서를 새 세션의 작업 지시서에 붙입니다.

**병렬 에이전트는 모듈당 하나만 둡니다.** 모듈 경계가 분명하면 git worktree로 모듈별 에이전트를 함께 돌릴 수 있습니다. 같은 모듈에 둘 이상을 넣으면 충돌을 정리하는 비용이 이득보다 큽니다. 통합은 사람이 하고, 통합 전 검증(계약 테스트, e2e)은 CI에 맡깁니다.

**인수인계 문서도 나눕니다.** 전역 `HANDOFF.md` 하나 대신 `domains/*/HANDOFF.md`로 나눕니다. 전역에는 진행 중인 작업 목록과 담당 모듈만 둡니다.

## 도입 순서

1. **모듈 지도 작성.** 에이전트에게 저장소를 분석하게 해서 목차형 L0 `CONTEXT.md`를 만듭니다.
2. **경계 감사.** 순환 의존과 경계 위반 지점을 목록으로 만듭니다. 심한 곳은 에이전트 투입을 미룹니다.
3. **시범 모듈 선정.** 경계가 깨끗하고 테스트가 있는 모듈 하나에서 L1·L2 문서와 작업 지시서 절차를 검증합니다.
4. **코드 검색 인프라.** 심볼 인덱싱을 먼저 하고 의미 검색은 뒤로 미룹니다.
5. **CI 강화.** 계약 테스트와 영향 범위 테스트를 넣습니다. 레거시 모듈은 특성화 테스트부터 씁니다.
6. **도메인 단위로 확산.** 시범 모듈에서 통한 문서와 인프라 패턴을 복제합니다.
7. **문서 검증 자동화.** 이 시점부터 문서를 손으로 관리하지 않습니다.

## 요약

- 10만 라인까지는 문서로 맥락을 주고 도구를 최소로 씁니다.
- 100만 라인부터는 모듈 경계로 맥락을 가두고, 검색 인프라로 조각을 주고, CI로 안전을 확인합니다.

규모가 커질수록 에이전트 관리는 프롬프트 문제에서 소프트웨어 엔지니어링 문제로 바뀝니다.
